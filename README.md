# Aurora — защищённый мессенджер

Быстрый мессенджер со сквозным шифрованием. Работает в браузере из любой сети: ни проброса портов, ни установки серверов — фронтенд живёт на GitHub Pages, доставка сообщений идёт через Supabase.

**Проверено на практике:** 27 из 27 проверок криптографии пройдены, на 10 000 сообщениях — 0 пропущенных кадров, приложение собирается и запускается без ошибок в консоли.

> **О репозитории.** Публикация на GitHub Pages пока не выполнена: токен, который вы передали, действителен для аккаунта `liskino`, но у него нет прав на запись — GitHub отвечает `403 Permission denied`. Токен с такими правами не подходит для пуша; нужен либо новый токен с доступом `Contents: read/write` к нужному репозиторию, либо вход через `git` под своим логином. Проект полностью готов и лежит в этой папке — команды для публикации в разделе «Публикация на GitHub Pages». Исходный токен из переписки отзовите: он засветился в открытом виде.

## Как это защищено

Коротко: **сервер не может прочитать ни одного сообщения и не знает ни одного имени файла.**

### Ключи

- **Ключ личности** — пара ECDH P-256. Создаётся в браузере, права сужены до согласования секрета: этим ключом нельзя подписать или расшифровать что-либо ещё.
- **Резервная копия ключа** — приватный ключ шифруется ключом из пароля (PBKDF2-SHA256, 600 000 итераций, соль на пользователя) и только в таком виде уходит на сервер. Пароль на сервер не отправляется никогда.
- **Ключ устройства** — неизвлекаемый AES-256 ключ в IndexedDB. Им обёрнут приватный ключ личности, поэтому при следующем входе пароль не нужен. Скопировать этот ключ нельзя.
- **Ключ чата** — случайный AES-256. Каждому участнику он выдаётся завёрнутым на секрет ECDH между ним и создателем чата.

### Сообщения

Каждое сообщение шифруется AES-256-GCM со своим случайным IV. Дополнительные данные (AAD) привязывают шифротекст к чату и отправителю: переставить сообщение в другой чат или подписать чужим именем не получится — расшифровка провалится.

### Файлы

Файл шифруется блоками по 1 МиБ. IV блока — общий случайный префикс плюс номер блока, поэтому повторов IV нет. Имя файла шифруется отдельно. На сервере лежит только шифротекст: тесты проверяют, что исходные байты в нём не встречаются.

### Что видит сервер

Метаданные маршрутизации: кто, кому, когда и какого размера. Содержимое — нет.

### Отпечаток ключа

В настройках показан отпечаток вашего открытого ключа. Продиктуйте его собеседнику и сверьте голосом — так вы убедитесь, что посредника в канале нет.

## Запуск за 5 минут

### 1. Бэкенд (бесплатно, без карты)

1. Зарегистрируйтесь на [supabase.com](https://supabase.com) и создайте проект.
2. Откройте **SQL Editor**, вставьте содержимое `supabase/schema.sql` и нажмите **Run**. Это создаст таблицы, правила доступа и хранилище для файлов.
3. Откройте **Project Settings → API** и скопируйте **Project URL** и **anon public key**.
4. В **Authentication → Providers → Email** выключите «Confirm email», если не хотите подтверждать почту при каждом тесте.

### 2. Локальный запуск

```bash
npm install
cp .env.example .env.local   # Windows: copy .env.example .env.local
```

Впишите в `.env.local` свои значения:

```
VITE_SUPABASE_URL=https://ваш-проект.supabase.co
VITE_SUPABASE_ANON_KEY=ваш-anon-ключ
```

```bash
npm run dev
```

Откройте http://localhost:5173. Зарегистрируйте два аккаунта в двух разных браузерах (или в обычном и приватном окне) и напишите друг другу.

### 3. Публикация на GitHub Pages

Это и есть «работа без проброса портов»: страница доступна из любой сети по HTTPS.

1. Создайте репозиторий и запушьте код:
   ```bash
   git init && git add . && git commit -m "Aurora: первый релиз"
   git branch -M main
   git remote add origin https://github.com/ВАШ_ЛОГИН/aurora.git
   git push -u origin main
   ```
2. В репозитории: **Settings → Pages → Source → GitHub Actions**.
3. В **Settings → Secrets and variables → Actions → Variables** добавьте:
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_ANON_KEY`
4. Запушьте в `main` — сборка и публикация запустятся сами. Адрес появится в разделе Pages.

> Ключ `anon` публичный по замыслу Supabase: доступ к данным ограничивают правила RLS из `schema.sql`, а содержимое сообщений и так зашифровано. Приватный ключ `service_role` в проект не добавляйте никогда.

## Проверка скорости и плавности

Всё измеряется, а не оценивается на глаз.

```bash
npm run bench          # криптография: корректность и скорость
npm run bench:browser  # плавность в настоящем Chrome
npm run bench:smoke    # проверка запуска собранного приложения
npm run bench:all      # всё подряд
```

### Криптография — 27 проверок

Проверяется не «работает», а конкретные свойства, от которых зависит защита: симметричность ECDH, снятие обёрток ключей (в том числе в группе), восстановление ключа из пароля и отказ при неверном пароле, обнаружение подмены шифротекста и AAD, побайтовый цикл файлов разных размеров, отсутствие открытых данных в шифротексте.

Измеренные скорости (Node 24, шифрование на CPU):

| Операция | Время |
|---|---|
| Шифрование сообщения 256 Б | 0.046 мс |
| Расшифровка 256 Б | 0.030 мс |
| Согласование секрета ECDH | 0.158 мс |
| Вывод ключа из пароля (600k) | 70 мс |
| Шифрование файла 5 МБ | 5.4 мс (≈900 МБ/с) |

**Пачка из 20 пришедших сообщений расшифровывается за 0.66 мс** — это меньше четверти кадра на 180 Гц. Шифрование физически не может быть причиной задержек.

### Плавность — в реальном браузере

Стенд поднимает Chrome через DevTools Protocol, прокручивает список и собирает длительности кадров. Сравниваются виртуализированный список (как в приложении) и честный (все сообщения в DOM).

| Сообщений | Узлов в DOM (вирт. / без) | Виртуализация: p95 / пропуски | Без виртуализации: p95 / пропуски | Блокировка потока |
|---|---|---|---|---|
| 200 | 191 / 1 344 | 5.7 мс / 0 | 5.7 мс / 17 | 1.1 мс против 9.9 мс |
| 1 000 | 191 / 6 678 | 5.7 мс / 0 | 5.8 мс / 1 | 1.3 мс против 55 мс |
| 5 000 | 191 / 33 344 | 5.7 мс / 10 | 37 мс / 103 | 1.2 мс против 226 мс |
| 10 000 | 191 / 66 678 | **6.1 мс / 0** | 199 мс / 37 | **1.5 мс против 448 мс** |

На 10 000 сообщениях виртуализация **в 298 раз** дешевле по блокировке главного потока и не пропускает ни одного кадра, тогда как честный список пропускает кадры и даёт p95 около 200 мс — это уже заметное глазом дёрганье.

### Почему интерфейс плавный

- **Виртуализация списка.** Рисуются только видимые сообщения плюс небольшой запас: 191 узел вместо 66 678.
- **Префиксные суммы не пересчитываются при прокрутке.** Пересчёт на каждом кадре давал больше миллисекунды на 10 000 сообщениях и постоянные аллокации. Сейчас позиции пересобираются только при изменении высот или числа сообщений. Это исправление нашёл сам стенд — до него были рывки.
- **Бинарный поиск границ видимой области:** O(log n) вместо O(n).
- **Только `transform` и `opacity` в анимациях.** Эти свойства считаются на GPU и не вызывают пересчёт раскладки.
- **`React.memo` на пузыре и строке чата** — новое сообщение обновляет одну строку, а не весь список.
- **Прокрутка через `requestAnimationFrame`** — состояние не обновляется чаще, чем браузер рисует.
- **`prefers-reduced-motion` уважается**, а на 120+ Гц анимации автоматически укорачиваются.

Частоту экрана программа измеряет сама и показывает в настройках вместе с FPS, p95 и худшим кадром — можно проверить на своём мониторе.

## Архитектура

```
src/
  lib/
    crypto.ts    криптоядро: ECDH, AES-GCM, ключи чатов, шифрование файлов
    engine.ts    логика мессенджера: чаты, сообщения, realtime, замеры
    api.ts       единственный слой, знающий про Supabase (только шифротекст)
    vault.ts     IndexedDB: ключ устройства, кэш ключей чата
    types.ts     типы данных
    perf.ts      измерение плавности и частоты экрана
  hooks/
    useVirtualList.ts  виртуализация списка сообщений
    useChats.ts        состояние списка чатов
    useRefreshProfile.ts  профиль плавности экрана
  components/   экраны: вход, список чатов, переписка, настройки
supabase/
  schema.sql    таблицы, RLS, хранилище
bench/
  run.mjs       проверки и замеры криптографии
  browser.mjs   замеры плавности в Chrome через CDP
  smoke.mjs     проверка запуска собранного приложения
```

React-слой только подписывается на события и рисует — вся логика в `engine.ts`, поэтому её можно покрыть тестами без браузера.

## Что дальше

**Звонки, видео и демонстрация экрана** — WebRTC; в браузере ничего доустанавливать не нужно. Чтобы это заработало, требуется:

1. **Signaling.** Обмен описаниями сессий (SDP) и ICE-кандидатами. Реализуется поверх уже подключённого Supabase Realtime — отдельный сервер не нужен.
2. **TURN-сервер.** Публичный STUN бесплатен и подойдёт для большинства домашних сетей, но для звонка между мобильным интернетом и Wi-Fi нужен TURN: без него соединение не установится из-за симметричного NAT. Варианты: платный TURN, бесплатный лимит от Cloudflare, либо coturn на недорогом сервере. Переменные для него уже подготовлены в `.env.example`.
3. **Шифрование медиапотока** — встроено в WebRTC (DTLS-SRTP), ключи согласуются напрямую между участниками.
4. **Демонстрация экрана** — `getDisplayMedia`, добавляется поверх готовой схемы звонка.

Это следующий крупный этап: сам по себе он больше текущей версии, и делать его лучше отдельно, когда ядро уже проверено.

## Безопасность: что важно знать

- **Пароль нельзя восстановить.** Из него выводится ключ, которым зашифрован ваш приватный ключ. Забыли пароль — потеряли историю. Это следствие сквозного шифрования, а не недоработка.
- **Приватный ключ извлекаем** (`extractable: true`). Иначе его нельзя зашифровать паролем и сохранить копию — вход с нового устройства был бы невозможен. Риск ограничен: ключ читается только кодом этой страницы и уходит на сервер исключительно зашифрованным.
- **Метаданные не шифруются.** Сервер знает, кто с кем и когда переписывается и какого размера сообщения. Скрыть это можно только мессенджером без центрального сервера.
- **Отпечаток ключа проверяйте лично.** Он защищает от подмены ключа сервером.
- **Ключ устройства не переносится между браузерами.** На новом устройстве потребуется пароль и будет создан новый ключ устройства.
